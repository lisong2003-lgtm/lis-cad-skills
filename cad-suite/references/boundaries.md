# 红线与已知缺陷清单

## 一、不可逾越的红线

1. **不产出工程量。** 本技能及 modules 内识图层的所有输出 `final_quantity=false`。
   吨位、体积、面积、长度、造价、结算量一律不出现；出现即视为缺陷。
2. **确认档不许自我升级。** 聚合层（project_aggregate）置信度固定 0.72、关系层固定 0.72，
   都低于 `confirmed_evidence` 的 0.90 门槛；只有直接证据（带语义图层与坐标的文字标注）才能进确认档。
3. **不伪造证据。**
   - 图层名解不出时用 `#句柄` 占位，`#` 前缀明确标注这不是真实名字，真实名字保持空。
   - 直径解析不出就判不可用并记 review，不猜。
   - 楼层判不出落 `unknown` 并记 review，不猜。
4. **图纸不出机。** 解析全在本机；manifest、回归报告含公司项目路径，只落本机工作区，不进发布包、不 commit。
5. **公司数据不上云、不推远端 Git。**

## 四、分发与部署边界

| 项 | 事实 | 后果 |
|---|---|---|
| `modules/cad-file-reader/vendor` | 符号链接，指向本机 `<skills-root>/cad-file-reader/vendor`（numpy / ezdxf / ezdwg，约 70MB） | 换机器或链接目标不存在时，**识图阶段直接失败**，下游全部 unavailable |
| `resync_modules.py` 的同步语义 | `copytree(symlinks=True)`，链接原样保留、不解引用 | 整个 `modules/` 约 5MB；一旦被解引用会涨到 60MB 并把可重装的依赖钉死进包 |
| `--check` 的比对口径 | 双向：缺失 / 内容不同 / 副本多余 | 旧版只遍历源侧，曾漏报 1740 个解引用出来的多余文件 |

**分发时必须说清**：本目录不是自包含的可分发包。要么随包附带 vendor 依赖，要么要求使用者
按 `cad-file-reader` 的依赖说明自行安装。把带断链的目录发给别人，对方会看到「一张图都读不出来」。

### ⚠️ 三端同步时必须排除 vendor（2026-10-30 真实事故）

`~/Documents/GitHub/lis-cad-skills/cad-file-reader/vendor` 是**指向 `<skills-root>/cad-file-reader/vendor` 的符号链接**，
而那里是 82MB 的实体依赖目录。用 `rsync -a --delete` 从仓库同步到安装目录时：

- 源侧 vendor 是链接 → rsync 认为目标侧的实体目录「多余」
- `--delete` 于是开始删目标里的文件，但它又删不掉非空目录
- 结果：**82MB / 2866 文件被删到 18MB / 657 文件**，`bin/`、所有 `*.dist-info`、各包的 `tests/` 全没了

正确做法：

```bash
# 同步 cad-file-reader 一律排除 vendor
rsync -a --delete --exclude 'vendor' cad-file-reader/ <workbuddy-skills-root>/cad-file-reader/
rsync -a --delete --exclude 'vendor' cad-file-reader/ <skills-root>/cad-file-reader/
```

修复办法（已实测）：按**锁定版本**重装，不要用 `>=` 让版本漂移——

```bash
python3 -m pip install --target <tmp> "ezdxf==1.4.5" "ezdwg==0.12.6" "numpy==2.5.4" \
    "fonttools==4.63.0" "pyparsing>=3.1" "typing_extensions>=4.10"
```

`ezdwg` 0.17.x 与 0.12.6 跨了大版本，直接装最新会悄悄改掉 DWG 解析行为。

## 五、ezdwg 版本是硬约束（2026-10-30 更新）

s10 当时把「18 张图读得出文字、读不出图层」判为文件特性，结论是「收益不抵风险，暂缓」。
**这个判断是错的——根因是 vendor 里的 ezdwg 0.12.6 有缺陷。**

| 版本 | 同一张 J-1结构.dwg 的图层名 |
|---|---|
| ezdwg 0.12.6 | 106 个图层，**解出 0 个名字**（全是空串） |
| ezdwg 0.17.2 | 106 个图层，**解出 106 个真名**（`DIM`/`COLU_HATCH`/`结_梁_实线`…） |

升级后 72 张真图回归：

| 指标 | s10（0.12.6） | 现在（0.17.2） |
|---|---|---|
| 成功解析 | 66/72 | **67/72** |
| 有文字无图层 | 18 张 | **0 张** |
| 主线（非 review）占比 | 95.1% | 待重测（图层全真实名，`#句柄` 降级不再触发） |

失败的那 5 张报 `section map has no entries` / `page info truncated`，是库仍不支持的
DWG 内部结构变体，`--allow-big` 无效，属真实边界。

**图层名为什么是硬约束**：算量技能按图层名找梁线（`梁-实线|BEAM`）、找板填充。
图层名一空，梁线一条都取不到，梁长和体积恒为 0。实测同一张 J-1结构：

| | 图层名空（0.12.6） | 图层名正常（0.17.2） |
|---|---|---|
| 边界线段 | 0 | 1047 |
| 中心线候选 | 0 | 251 |
| 有长度/截面对象 | 0 | 84 |
| 混凝土净候选 | **0.00 m³** | **81.76 m³** |

**所以 `requirements.txt` 写死 `ezdwg>=0.17.2`，低于这个版本算不出混凝土量。**

## 六、算量入口的三个坑（都已修，改动在 tujian-suanliang）

1. **`--floor-label` 的语义是图框标题，不是楼层号。** `beam_instances_for_label` 用
   `sheet_label == floor_label` 精确比对；而 `find_sheet_bbox` 用模糊包含比对。
   两处口径不一致，导致传 `-0.050` 能找到图框却找不到梁标注。正确值形如 `-0.050梁平法施工图`。
2. **负值必须以 `--opt=value` 形式传。** `["--floor-label", "-1F"]` 会被 argparse 当成选项，
   报 `expected one argument`。原代码给 `--bbox` 修过这个坑，`--floor-label` 的 8 处漏了。
3. **复用几何时路径要一起重指向。** `support_label == beam_label` 时走 `_reused_step` 只记了
   「复用」，没改 `support_geometry` 变量，下游 `--support-dxf` 会去打开一个从未生成的
   `support_geometry_<hash>.dxf`，报 `FileNotFoundError`。

## 七、跨专业对照的三个坑（都已修，改动在 cad-file-reader + cad-suite）

1. **只按「同层」配对是错的。** 实测 J 地块屋面层把 3 张「J-5#/J-8#/J4,6,7# 防火节能专篇」
   配进了结构配筋图里。专篇是报审文件，图上没有可对照的构件位置，"配上了"反而误导下游。
   现在按图种分三档：`admin`（目录/总说明/专篇/系统图）不配对、`detail`（大样/详图）只配大样、
   `plan`（布置/配筋/平立剖）平面配平面。
2. **楼层判不出来时不能就地堆在一起。** `J-1结构`/`J-2#`/`J-5结构`/`J-8#` 这类成套楼栋图
   覆盖全楼各层，本就没有单一楼层，全落在 `unknown`；按楼层分组会让 4 栋楼的结构图与
   4 栋楼的建筑图堆成一大组。改为按楼栋号分，配对从 2 组变成 8 组，且每组都能对上号。
   楼栋号要同时认 `J-3#4#6#7#`（数字# 连写）和 `J4，6，7#`（逗号列表）两种写法，只认一种必漏。
3. **同名不同专业的图纸产物互相覆盖。** 「建筑/某项目二区J-5#楼（改消防）.dwg」与
   「电气/某项目二区J-5#楼（改消防）.dwg」完全同名，s1a 的 detail 与 s1b 的 structural
   都按图名命名 → 61 张图只出 59 份产物，**丢掉的恰是建筑图**，表现为「J-5/J-8 楼栋
   死活配不上建筑图」。现在冲突时加父目录前缀（`电气_xxx`），不冲突的保持原名。
   > 这条的教训：配对配不上时，先数产物份数是否等于图纸张数，再谈算法。

## 八、钢结构 / 市政的真图底牌（2026-10-30 实测）

扫全盘 8071 张（DWG 6092）：钢结构关键词命中 8 张，**真正钢构件图只有 1 张**；市政管网命中 49 张，**真管网图 3 张**。

| 类别 | 能做到 | 做不到 |
|---|---|---|
| 钢结构 | 认 H 型钢/圆管/槽钢截面（`H2000x600x36x60` 这类四段式写法）、材质 Q355/Q390/Q460、支座/加劲肋/焊缝/螺栓/高强螺栓 | **不出重量**（没做几何段按构件线归并，没有长度就没有吨位）；门式刚架/网架/索膜无样本 |
| 市政 | 管线候选 949/1363 条，带系统、规格（DN/De）、坐标；构件级系统归属 | 无「井—管段—井」拓扑闭合，算不出管长、做不了挖填方；三张图的井号引用都是 0 |

**验这两类图时先看两个数**：截面数、管线候选数。数少不一定是失败——
ALC 钢立柱布置图与钢柱预埋排版图本就没有型钢截面，总平面分区图本就不是管网图，硬凑数才是错。

已知误判（不修，属粘连文字的固有代价）：`[2003` 是 `[20`（槽钢）与相邻编号 `03` 合并成一段文字，
会被认成槽钢截面；合成数据测不出来，只有真图会暴露。

| 级别 | 做什么 | 状态 |
|---|---|---|
| 一级：配对 | 定哪两张图该放一起看（按楼层/楼栋定范围，按图种分档） | 完成。J 地块 61 张 → 10 组配对 |
| 二级：轴网核对 | 比轴线位置/总跨/开间，确认是不是同一片区域 | **已可用**。10 组里通过 3 组、部分重叠 1 组、判不了 6 组 |
| 三级：构件级对照 | 逐项比构件位置/标高/洞口 | **没做**，需人工看图 |

### 9.1 轴号文字这条路走不通，改走几何

0.38.6 试过靠正则抓轴号文字，实测 80786 条候选里只有 448 条（0.6%）落在轴网图层，
过滤后单张图只剩 1~6 个轴号还有 `CEN`/`con` 残留。真正的原因是：**轴号在天正转出的图里
基本不在独立文字图层上**（实测轴网图层上 0 条文字）。

0.38.7 换成几何口径（`cad-file-reader/scripts/cad_axis_net.py`）：轴线本身一直在图上——
一组等长、平行、等距重复的直线。只认几何、不认文字，输出方向/轴数/总跨/开间序列。

三道判据：① 必须落在轴网图层；② 单段 ≥2m；③ 同长度组内按位置排序成簇
（视图间空档远大于轴距，自动断开，但断开阈值不超过 30m——否则同一根轴在多视图里的
副本会被连成一条 255m 的假轴网）。

### 9.2 两个必须记住的坑

**坑一：轴线常被切碎**。天正导出的轴线会被切成多段（实测 `J-2#` 轴网层最长线段只有 3000mm，
而该楼轴距 6~9m）。不先接起来，「轴线最短 2m」这条判据会把「被切碎的轴」判成「图上没有轴」。
所以加了共线拼接，但**只在原始线段提不出该方向轴网时才启用**——完整轴线拼接后端点不齐，
长度分组会漂，实测会把建筑图从 25 轴并成 20 轴、轴距从 3000 变成 3600，反而把对的判成错的。

**坑二：LibreDWG 转出的 DXF 几何全空**。`J-2#`/`J-3#4#6#7#` 是 R2007 格式，直读失败后转 DXF，
但产出的 DXF 缺 `EOF` tag、实体 handle 重复、图层名为空，`ezdxf.readfile` 抛 `DXFStructureError`，
连 `recover.readfile` 也救不了。后果是这两张图的几何段为空，对照直接判「无法比对」。
实际文件里的 LINE 数据是完整的——已加 `dxf_geometry_stream` 按 group code 流式扫，
J-2# 取回 5269 段、J-3#4#6#7# 取回 8002 段。

### 9.3 判定口径（别说成「已证明是同一栋楼」）

主判据是**结构侧覆盖**：结构柱网通常只是建筑轴网的子集（建筑多出外墙轴、门窗定位轴），
用两侧最大值会让「结构只对上 3 个开间、建筑有 30 个」也算一致。
开间还支持「段和」匹配：结构一个 3300 开间，建筑图可能被隔墙定位轴拆成 1650+1650，
只比等值会把这种正常情况算成对不上。

J 地块实测：屋面 35/35 轴完全一致、J-1 9/25 开间全覆盖、J-5 14/20 覆盖 92%（判一致）；
J-8 结构图只画局部、跨差 26.8%（判部分重叠）。

**这个模块能证明「不一致」，不能证明「是同一栋」**：同户型不同楼栋共用同一套轴网，
间距会完全一致——实测 J-1 结构 × J-5 建筑同样判「一致」（这两栋本就是同户型）。
所以「轴网一致」的正确读法是「两图描述同一类平面」，楼栋/范围仍需人工确认。

### 9.4 口径

`s4-compare` 在轴网核对无一通过时记 `degraded`，文案写明「构件级对照未执行，需人工看图核对」；
有通过组时才记 `ok`，并如实给出「通过 N 组 / 不对应 M 组 / 判不了 K 组」。
以前这里记 `ok` 并说「N 个楼层可跨专业对照」，是假进度——配对成功不等于对照完成。
